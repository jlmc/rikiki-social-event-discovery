# rikiki web (static site, GitHub Pages)

A browser-based search UI over the same real cultural/family events as
[`../cli`](../cli/README.md) and [`../mobile-app`](../mobile-app/README.md) — open a URL, no
phone and no Expo Go needed, unlike the mobile app. Select filters, search, and browse results
as cards, each with a "see full details" popup and a link to the event's official page.

## Why this exists as a third module, not just the mobile app opened in a browser

Neither the CLI's Docker pipeline nor a plain "point a browser at the 4 real sources" approach
works on GitHub Pages, for two separate reasons that both have to be worked around at once:

1. **GitHub Pages only serves static files.** It cannot run a server, so there's nowhere to
   put the scraping code if it needs to run "live," on every visit.
2. **None of the 4 real sources allow direct browser `fetch()` calls** (no CORS headers — see
   [`mobile-app/README.md`](../mobile-app/README.md#why-this-isnt-just-a-website)). This is
   why the mobile app exists as React Native rather than a web page in the first place.

The fix: the scraping runs periodically in **GitHub Actions** (a real server, just not one we
operate — see [`.github/workflows/publish-web.yml`](../.github/workflows/publish-web.yml)),
which reuses [`../cli/collect-events.js`](../cli/collect-events.js) unchanged, and publishes
the result as `events.json` right next to this static site. The browser only ever fetches that
one same-origin file — never the 4 sources directly — so there's no CORS problem, and no
server is needed at the time someone visits the page. Filtering itself is instant and
client-side; only the underlying pool of events is refreshed periodically (every 6 hours) by
the workflow, not on every search.

## Files

- **`index.html` / `style.css` / `app.js`** — the static page: a filter form, a card grid, and
  a details modal. Vanilla JS, no framework, no build step.
- **`lib/filter-events.js`** — the date/location/type filtering rule, ported line-for-line from
  [`../cli/lib/filter-events.js`](../cli/lib/filter-events.js) (and identical to the mobile
  app's copy) — all three front-ends agree on what a filter matches.
- **`events.json`** — **not committed** (same as `cli/events.json` — see the root
  `.gitignore`). Generated by the GitHub Actions workflow at deploy time; for local testing,
  copy a real one from a `cli/` run: `cp ../cli/events.json events.json`.

## Running it locally

Any static file server works, since this is plain HTML/CSS/JS with no build step — e.g.:

```bash
cd web
cp ../cli/events.json events.json   # or run ../cli/list-events.sh first to generate one
python3 -m http.server 4321
```

Then open `http://localhost:4321`. (ES modules need `http://`, not `file://` — a plain
double-click on `index.html` won't load `app.js`'s import correctly.)

## Publishing (one-time setup)

The workflow deploys automatically once GitHub Pages is configured to build from Actions:

1. On GitHub, go to the repository's **Settings → Pages**.
2. Under **Build and deployment → Source**, choose **GitHub Actions**.

After that, [`publish-web.yml`](../.github/workflows/publish-web.yml) runs on a 6-hour
schedule, on every push to `master` that touches `web/`, `cli/collect-events.js` or
`cli/providers/`, and on-demand from the Actions tab (**Run workflow**) — each run re-scrapes
the real sources and republishes the site with fresh data.
